CSC376 robot interface

csc376_franky is the Python interface to the CSC376 teaching lab’s Franka Emika Panda robots. You plan and preview a trajectory on a station’s GPU PC with the Toolbox, and the station’s miniPC runs it on the robot. It lives in the robot-interface/ folder of the course fork and is not part of the upstream Toolbox.

GPU PC (two per station)
┌──────────────────────────────────────────────────┐
│ your script or notebook                          │
│   csc376_franky.motion_generator    plan         │
│   csc376_franky.visualizer          preview      │
│   FrankaJointTrajectoryController   run          │
└──────────────────────────────────────────────────┘
      │ trajectories              ▲ state, 50 Hz
      ▼ TCP 7376                  │
miniPC 192.168.1.100
┌──────────────────────────────────────────────────┐
│ csc376-robot-server                              │
│   checks every trajectory                        │
│   1 kHz joint impedance control                  │
│   one trajectory at a time                       │
│   PREEMPT_RT, libfranka 0.9.2                    │
└──────────────────────────────────────────────────┘
      │ FCI                       ▲
      ▼ 1 kHz torque control      │
Panda 192.168.1.107, with its Franka Hand

  • GPU PC: csc376_franky, pure Python. It plans with the Toolbox and Ruckig, previews in Swift, and talks to the miniPC. It needs no libfranka, no real-time kernel and no compiler, so it runs on any lab PC.

  • miniPC: the robot server (robot-interface/server/). It is the only program that talks to the robot. It checks every trajectory, runs a joint impedance controller at 1 kHz, and sends the robot’s state to the GPU PCs.

Both GPU PCs of a station can work at the same time. Each one sees the robot’s state, so each can plan and preview from where the robot actually is. The robot runs one trajectory at a time.

Quick start

On a station’s GPU PC, with FCI active in Desk and the user stop in reach:

import roboticstoolbox as rtb
from spatialmath import SE3

from csc376_franky import FrankaJointTrajectoryController
from csc376_franky.motion_generator import RuckigMotionGenerator
from csc376_franky.visualizer import RtbVisualizer

robot = FrankaJointTrajectoryController()  # the robot server on this station's miniPC
panda = rtb.models.Panda()
motion_generator = RuckigMotionGenerator()

q_start = robot.get_current_joint_positions()
se3_start = panda.fkine(q_start)
se3_target = SE3.Ty(0.1) * se3_start  # 10 cm along the base y axis

cartesian_traj, dt = motion_generator.calculate_cartesian_pose_trajectory(
    se3_start, se3_target
)
q_traj = motion_generator.cartesian_pose_to_joint_trajectory(
    panda, q_start, cartesian_traj
)

visualizer = RtbVisualizer(panda, q_start, real_robot=robot)  # see the plan first
visualizer.run_joint_trajectory(q_traj, dt)

robot.run_joint_trajectory(q_traj, dt)  # then run it on the robot
robot.move_gripper(0.0)  # close the gripper

visualizer.stop()  # ends the render thread, so that Python can exit

Setup

Lab GPU PCs: nothing to install. The shared csc376 environment has the Toolbox, Ruckig and csc376_franky, and the examples, to copy into your home:

conda activate csc376
cp -r "$CONDA_PREFIX/share/csc376_franky/examples" ~/csc376_franky_examples
cd ~/csc376_franky_examples && python visualize_then_execute_trajectory.py

Dev container: nothing to install either; it installs csc376_franky from robot-interface/ in editable mode.

Anywhere else: install the Toolbox from the course fork as its README says, then, from robot-interface/:

pip install -e ".[planning]"

The robot server’s address defaults to 192.168.1.100:7376, the miniPC on every station’s robot network. FrankaJointTrajectoryController(host, port), or the environment variables CSC376_ROBOT_HOST and CSC376_ROBOT_PORT, change it.

There is no robot at home, but the robot server can drive a simulated one: see Trying it without a robot.

Planning and previewing

Planning a trajectory

RuckigMotionGenerator plans a straight move of the end effector between two poses, in two steps:

  1. calculate_cartesian_pose_trajectory() interpolates from se3_start to se3_target with Ruckig, which limits the velocity, acceleration and jerk. It returns the Cartesian trajectory and the time between its points, dt (0.01 s).

  2. cartesian_pose_to_joint_trajectory() solves the inverse kinematics of every point with the Toolbox, each one starting from the solution of the point before it. It returns the joint trajectory that the visualizer and the robot run.

The three factors of calculate_cartesian_pose_trajectory scale the Panda’s Cartesian limits from its datasheet, for translation and for rotation:

Factor

Default

Limits

relative_vel_factor

0.02

1.7 m/s, 2.5 rad/s

relative_acc_factor

0.01

13 m/s², 25 rad/s²

relative_jerk_factor

0.05

6500 m/s³, 12 500 rad/s³

Three things to know when planning:

  • Plan from where the robot is. The trajectory starts at se3_start itself, and the miniPC refuses a joint trajectory that does not start at the robot’s measured joint positions, so take q_start from get_current_joint_positions().

  • The orientation is interpolated as a rotation vector, component by component. That only follows a rotation about a fixed axis when the start and target orientations are close: plan a large reorientation as several short moves.

  • cartesian_pose_to_joint_trajectory raises RuntimeError when the inverse kinematics finds no solution for a pose, for example a target out of reach.

A trajectory does not have to come from the motion generator. The robot runs any N x 7 array of joint positions that passes the miniPC’s checks (see What the miniPC checks).

Previewing in Swift

RtbVisualizer opens Swift in the browser and shows a Panda at q_start. run_joint_trajectory() plays a joint trajectory on it with the timing it will have on the robot, and move_gripper() moves its fingers.

With real_robot=robot, a translucent blue Panda follows the real robot live, so the preview can be compared with where the robot really is.

Call stop() when the program is done: it ends the render thread and closes Swift.

Preview, then robot

RobotWrapper puts the two together. Its run_joint_trajectory plays the trajectory in Swift after you press enter, then runs it on the robot after you type yes:

from csc376_franky.robot_wrapper import RobotWrapper

robot = RobotWrapper(
    has_visualizer=True, run_on_real=True, panda_rtb_model=panda, q_start=panda.qr
)
q_start = robot.get_current_joint_positions()  # the real robot's, if there is one
...
robot.run_joint_trajectory(q_traj, dt)
robot.stop()

With run_on_real=False nothing connects to the robot server, and the same program runs in Swift only. ip_address is the address of the station’s miniPC (the robot server), not of the robot; leave it out for the default.

Running on the robot

FrankaJointTrajectoryController is a network connection to the robot server. Its constructor waits until the miniPC is connected to the robot, so FCI must be active in Desk. Close it with close(), or use it as a context manager:

with FrankaJointTrajectoryController() as robot:
    print(robot.get_current_joint_positions())

Reading the robot’s state

The miniPC sends the robot’s state 50 times a second, so what these return is at most 20 ms old:

  • get_current_joint_positions(): the measured joint positions, an array of 7 [rad].

  • get_current_pose(): the end-effector pose (the Franka Hand’s TCP) in the base frame, as an SE3. It is the robot’s own forward kinematics, and agrees with rtb.models.Panda().fkine(q) when Desk’s end effector is the Franka Hand.

  • get_current_robot_state(): a RobotState, with the field names of libfranka’s franka::RobotState (q, dq, tau_J, O_T_EE, …).

Running a trajectory

run_joint_trajectory() sends an N x 7 joint trajectory and the time between its points, and waits until the robot has finished and settled. It returns ErrorCodes.Success, and raises RobotError if the miniPC refused the trajectory or the motion did not finish. error.code is the ErrorCodes value and error.message says what to change:

from csc376_franky import ErrorCodes, RobotError

try:
    robot.run_joint_trajectory(q_traj, dt)
except RobotError as error:
    if error.code == ErrorCodes.RobotBusy:  # the other GPU PC has the robot
        robot.wait_until_idle()
        ...  # then plan again from get_current_joint_positions()
    else:
        raise

Between the points of a trajectory the miniPC interpolates at 1 kHz. A small gap between the first point and the robot (within the start tolerance) is blended out over 0.25 s, so the robot never jumps at the start.

set_trajectory_callback() registers a function that is called with the index of each point as the robot passes it, for example to log or to act part of the way through.

Stopping

stop() and Ctrl+C slow the robot to rest along its path within 0.5 s. Any client can stop any trajectory. stop() returns whether there was one to stop; a stop that comes too late to end the trajectory short of its last point does not interrupt it, and run_joint_trajectory returns ErrorCodes.Success.

The miniPC also stops a trajectory when the program that started it disconnects or has not been heard from for 2 s.

Warning

The user stop on the robot always works and does not depend on any of this. Keep it in reach whenever the robot can move.

After a reflex (usually a collision) the robot refuses to move, and requests fail with RobotNotReady. Check the robot and its surroundings, then call recover().

Moving home

move_home() moves the robot the way libfranka’s examples do, without Ruckig or the Toolbox. The miniPC runs libfranka’s example MotionGenerator through the robot’s own joint position controller, going straight in joint space from wherever the robot is to protocol.HOME_JOINT_POSITIONS, (0, −π/4, 0, −3π/4, 0, π/2, π/4).

Warning

Nothing is planned or previewed on the GPU PC, so check that the way is clear first.

speed_factor (0.2 by default) can be at most the miniPC’s velocity scale, 0.3. stop(), Ctrl+C and the miniPC’s other checks work as they do for a trajectory.

The gripper

robot.gripper is the station’s Franka Hand, a Gripper (None if the robot server runs without one). move_gripper() is a shortcut for its move:

robot.move_gripper(0.08)  # open to 8 cm, at 0.1 m/s
grasped = robot.gripper.grasp(width=0.03, speed=0.1, force=20.0)
print(robot.gripper.width, robot.gripper.is_grasped)

homing, move, grasp, open and stop wait until the gripper has finished and return whether it succeeded. Each has an _async variant that returns a concurrent.futures.Future of the same result instead of waiting. Gripper() on its own opens a connection of its own, for a program that only uses the gripper.

What the miniPC checks

The miniPC never trusts a trajectory. It refuses one, with a message saying what to change, unless all of these hold. The defaults are set on the miniPC.

0.05 rad

TrackingErrorTooLarge (the motion stops)

The velocity check compares consecutive points, and the acceleration check compares consecutive segments: the change of a joint’s step from one segment to the next, divided by dt². A trajectory from Ruckig passes easily. One that reverses or turns a corner at a single point may not: spread the change of velocity over several points. The first and last segments are not compared with rest, so a constant-velocity trajectory (np.linspace between two joint positions) is accepted.

Two GPU PCs, one robot

  • Both receive the robot’s state; get_current_joint_positions() is at most 20 ms old.

  • While one PC’s trajectory runs, the other’s run_joint_trajectory raises RobotBusy, naming the PC that has the robot. is_executing and wait_until_idle() let you wait for it.

  • Afterwards, a plan made before the robot moved no longer starts where the robot is, so the miniPC refuses it. Plan again from get_current_joint_positions().

  • The gripper is shared the same way: one command at a time, and not while the other PC’s trajectory runs.

  • RtbVisualizer(..., real_robot=robot) adds a translucent blue Panda that follows the real robot, so each PC sees when the other one moves it.

Trying it without a robot

The robot server can drive a simulated Panda and gripper, on any Linux or macOS machine with a C++17 compiler. From robot-interface/:

pip install . ./server                          # builds the controller
python -m csc376_franky_server --sim --bind 127.0.0.1
CSC376_ROBOT_HOST=127.0.0.1 python examples/sim_or_real_trajectory_with_wrapper.py

The simulated robot goes through the same checks as the real one, so a trajectory that it refuses would be refused in the lab too. --sim-speed 4 runs it four times faster than real time.

API reference

The robot and its gripper

class csc376_franky.FrankaJointTrajectoryController(host=None, port=None, *, timeout=10.0, wait_for_robot=True)

The station’s Panda, through the robot server on the miniPC.

host and port default to $CSC376_ROBOT_HOST and $CSC376_ROBOT_PORT, or the miniPC’s address on the station’s robot network (192.168.1.100:7376). The constructor waits until the miniPC is connected to the robot, so FCI must be active in Desk. Use it as a context manager, or call close().

close()

Disconnect. A trajectory this program started is stopped.

wait_for_robot(timeout=10.0)

Wait until the miniPC is connected to the robot and reports its state.

get_current_robot_state()

The latest RobotState from the miniPC (at most 20 ms old).

get_current_joint_positions()

The measured joint positions [rad], as an array of 7.

get_current_pose()

The measured end-effector pose (Franka Hand TCP) in the base frame, as an SE3.

This is the robot’s own forward kinematics. It agrees with rtb.models.Panda().fkine(q) when Desk’s end effector is the Franka Hand.

get_status()

The server’s latest state message as a dict: robot, trajectory and gripper.

property is_executing

True while the robot runs a trajectory, for this or any other client.

wait_until_idle(timeout=None)

Wait until no trajectory is running; False on timeout.

set_trajectory_callback(trajectory_callback)

Call trajectory_callback(index) for each point of a running trajectory.

It runs in the thread that called run_joint_trajectory, as the robot passes each point (a few points at a time, at the state rate).

run_joint_trajectory(joint_trajectory, dt)

Execute a joint trajectory on the robot and wait until the robot has stopped.

joint_trajectory is N x 7 joint positions [rad], dt seconds apart. The first must be the robot’s current joint positions: plan from get_current_joint_positions(). Returns ErrorCodes.Success, and raises RobotError if the miniPC refused the trajectory or it did not finish (e.code says why). Ctrl+C stops the robot along its path, then raises KeyboardInterrupt.

move_home(speed_factor=0.2)

Move to libfranka’s home pose (protocol.HOME_JOINT_POSITIONS) and wait until the robot is there.

The miniPC moves the robot as libfranka’s examples do: their MotionGenerator, followed by the robot’s own joint position controller, from wherever the robot is. Nothing is planned on this PC. speed_factor scales libfranka’s joint velocity and acceleration limits, up to the server’s velocity scale (0.3 by default). Returns ErrorCodes.Success and raises RobotError like run_joint_trajectory; Ctrl+C stops the robot, then raises KeyboardInterrupt.

stop()

Stop the running trajectory, whichever client started it: the robot slows to rest along its path within about half a second. Returns True if there was a trajectory to stop.

recover()

Clear the robot’s error after a reflex (e.g. a collision) so it can move again. Check the robot and its surroundings first.

move_gripper(width, speed=0.1)

Move the gripper fingers to width [m] at speed [m/s].

static setupSignalHandler()

Not needed any more: Ctrl+C during run_joint_trajectory stops the robot.

join()

Not needed any more: the control loop runs on the miniPC.

calculate_cartesian_pose_trajectory(se3_start, se3_target, relative_vel_factor=0.02, relative_acc_factor=0.01, relative_jerk_factor=0.05)

Interpolates and creates a smooth cartesian trajectory (smooth vel, acc, jerk maybe) starting from se3_start and ending at se3_target. The trajectory also follows the given cartesian constraints: relative_vel_factor, relative_acc_factor, and relative_jerk_factor which implicitly converts to a joint constraint :).

The rotation vector’s components are interpolated linearly, which only follows a rotation about a fixed axis when the start and target orientations are close. Plan a large reorientation as several short moves.

Parameters:

  • se3_start (SE3) – The start end-effector pose of the trajectory. Usually the current ee pose of the robot.

  • se3_target (SE3) – The end end-effector pose of the trajectory.

  • relative_vel_factor (float) – 0-1 multiplication factor to multiply PANDA_VEL_LIM_CARTESIAN. Limits the cartesian velocity during the entire trajectory.

  • relative_acc_factor (float) – 0-1 multiplication factor to multiply PANDA_ACC_LIM_CARTESIAN. Limits the cartesian acceleration during the entire trajectory.

  • relative_jerk_factor (float) – 0-1 multiplication factor to multiply PANDA_JERK_LIM_CARTESIAN. Limits the cartesian jerk during the entire trajectory.

Return type:

tuple[list[list], float]

Returns:

  • cartesian_pose_traj (list[list]) – List of a List: [[x, y, z, rx, ry, rz, elbow_angle], … ]. Cartesian pose trajectory of the end effector, from se3_start (at time 0) to se3_target.

  • self.dt (float) – Delta time between trajectory points of the cartsian_pose_traj.

Wire protocol

The wire protocol between the GPU PCs (csc376_franky) and the robot server on the station’s miniPC (csc376_franky_server).

Each client holds one TCP connection. Every message is a JSON object on one line.

A request, client to server:

{"op": "execute", "id": 7, "trajectory": [[q0, ..., q6], ...], "dt": 0.03}

A request without an “id” is a notification and gets no reply (the heartbeat). The server answers each request once, when it has finished:

{"id": 7, "ok": true, "result": {...}}
{"id": 7, "ok": false, "error": {"code": -7, "name": "...", "message": "..."}}

and sends the robot’s state to every client, state_rate times a second:

{"event": "state", "time": ..., "robot": {...}, "trajectory": ..., "gripper": {...}}

Requests: hello (first), state, ping, heartbeat, execute, move_home, stop, recover, gripper_homing, gripper_move, gripper_grasp, gripper_stop.
